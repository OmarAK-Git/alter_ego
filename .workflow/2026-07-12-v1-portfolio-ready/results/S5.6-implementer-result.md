# S5.6 Implementer Result — max_profile_build_block_days supervisor escalation

**Date:** 2026-07-13  
**Packet:** S5.6-implementer

## Summary

Wired `max_profile_build_block_days` in the profile builder. Entities with active uncleared alerts (`new` / `acknowledged` / `investigating`) that remain build-blocked longer than the configured threshold emit an auditable `DecisionRecord` with `profile_build_block_supervisor_escalation`, structured `block_days` / SLA metadata, and a warning log. Independent of S5.5 staleness escalation. Did **not** change scoring weight values or edit `state.json`.

## Design choices

- **Block duration:** days since earliest active alert, using linked `DecisionRecordModel.timestamp` (fallback: `AlertWorkflowStateModel.updated_at`).
- **Threshold:** strict `block_days > max_profile_build_block_days` (default 30, unchanged).
- **Escalation signal:** `DecisionRecord` with `event_id="PROFILE_BUILD"`, `is_anomaly=False`, flag `profile_build_block_supervisor_escalation` plus `block_days`, `max_profile_build_block_days`, `sla_hours=24`.
- **No-events path:** escalation still runs when `events_hist` is empty (early-return branch commits escalation decisions).
- **Return type:** `build_profiles()` still returns `int` profile count; escalations are queryable via decisions table.
