## Why not A (minimal ship)

A credible minimal ship would require at minimum:

1. **Artifacts:** `config/asset_classification.yaml` + `config/service_dependency_map.yaml` (or equivalent) with entity-id or role→asset mapping for synthetic/demo entities (`user_engineer_*`, `svc_*`).
2. **Loader:** read-only module (e.g. `core/asset_context.py`) with tests.
3. **Enrichment:** map `entity_id` → `asset_class`, `blast_radius` tier, optional `downstream_services[]` for `svc_*`; emit `infrastructure_volatile` flag where map says so.
4. **Persistence vs compute-time:** either new decision fields (schema + migration) or API-time join from static map — both touch multiple layers.
5. **API:** expose enrichment on `/api/alerts` and detail.
6. **UI:** blast-radius indicator column/badge; optional asset-class filter — **must not** show a fake indicator for all entities.
7. **Tests:** loader unit tests + web API tests.

Estimated scope: **medium packet**, comparable to S2.7 lifecycle ship (which was rejected). **No half-done path** — zero artifacts, zero loader, zero UI surface.

Stubbing `blast_radius: "unknown"` or a static "low" badge for every alert would violate packet constraint ("must not claim UI/API asset blast-radius that is not implemented").
