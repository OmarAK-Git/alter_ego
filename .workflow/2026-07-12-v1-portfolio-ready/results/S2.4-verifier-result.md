"Observation-count confidence is `n/(n+k)` with `confidence_k` in `scoring_config.yaml`; config is actually read; tests prove k changes confidence and larger n raises confidence."

## Verdict

## Strongest reason

## Reward-hack / residual risks (did not refute)

1. **`test_confidence_formula_from_yaml_config` alone is weak against default coincidence** — YAML k=10 equals the code fallback `10.0`, so that test alone would pass if scorer ignored the key. Closed by `test_confidence_k_override_changes_confidence` (non-default k) and the independent mutate-loaded-config probe (k=7).
2. **Pydantic `ScoringConfig` (`core/schemas/config.py`) does not declare `confidence_k`** — runtime path uses raw YAML dict via `load_scoring_config()`, so production scoring is unaffected; schema lag is debt, not an AC miss.
3. **Scorer was not edited in S2.4** — formula + `config.get` already present; packet AC5 explicitly allows this if YAML key + config-read tests land. Confirmed.
4. **Stale sibling test** `tests/worker/test_scorer.py::test_confidence_not_hardcoded` still documents “weighted average of per-feature confidences” (obsolete vs observation-count formula) and currently fails on missing `profiles` table under cohort gating — orthogonal to S2.4 ACs; not used as evidence for this claim.

These weaken the strength of the YAML-only formula test in isolation but do not break packet acceptance or the production wiring.
