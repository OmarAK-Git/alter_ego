# S5.3 Researcher Result — Postgres INSERT-only DB roles

**Date:** 2026-07-13  
**Question:** How should v1 enforce Postgres INSERT-only roles for audit (+ profile commit) tables given profile promotion currently UPDATEs rows?

**Recommendation: A — ship (with documented profile lifecycle-column exception)**

Ship an Alembic migration plus compose wiring for a least-privilege `alter_ego_app` runtime role. Enforce **true INSERT-only** on immutable commit/audit tables (`audit_logs`, `decisions`, `explanations`, `scoring_configs`). Enforce **payload immutability** on `profiles` via column-level `UPDATE` grants on `promoted_at` and `superseded_at` only — the minimum needed to keep `batch/profile_builder/builder.py` and `worker/profile_store.py` promotion paths working without Python changes. Amend SPEC_V3 §6.3 to state lifecycle columns are the sole DB-writable fields on committed profile rows.

Path B (audit-only INSERT + full profile INSERT-only downgrade) is viable but weaker than necessary: column grants ship honest profile-payload protection within the stated write scope. Path C (doc-only) is unnecessary — roles can ship without app code changes.

---

## Decision summary

v1 can close the portfolio DB-role gate **without expanding beyond `alembic/`, `docs/`, `docker-compose.yml`** by:

1. Creating `alter_ego_app` (runtime) while retaining bootstrap owner `user` for migrations.
2. Granting INSERT-only (plus SELECT) on append-only tables the app already treats as immutable.
3. Granting `INSERT` + `UPDATE (promoted_at, superseded_at)` on `profiles` — not literal table-level INSERT-only, but honest payload immutability aligned with frozen Pydantic `ProfileArtifact`.
4. Granting normal read/write on operational tables (`events`, `resolved_events`, `containment_queue`, `alert_workflow_state`, `eval_ground_truth`).
5. Running `alembic upgrade head` as owner via inline `DATABASE_URL` override in the web container startup command; runtime services use the app role URL.

Do **not** claim full table-level INSERT-only on `profiles` without a promotion redesign (out of scope).

### Feasibility within write scope (no Python required)

| Requirement | In-scope approach |
|---|---|
| Migration creates role + grants | New `alembic/versions/*.py` with `op.execute()` DDL |
| Alembic runs as owner | `docker-compose.yml` web `command` prefix: `DATABASE_URL=postgresql://user:password@... alembic upgrade head && DATABASE_URL=postgresql://alter_ego_app:...@... uvicorn ...` — `alembic/env.py:23` reads `settings.database_url` from env |
| Runtime uses app role | Set `DATABASE_URL` to app DSN on `web`, `worker`, `batch` services |
| Sequence privileges | `GRANT USAGE, SELECT ON SEQUENCE` for `audit_logs_log_id_seq`, `containment_queue_queue_id_seq` (required for INSERT with serial PKs) |
| Column-level profile UPDATE | PostgreSQL supports `GRANT UPDATE (promoted_at, superseded_at) ON profiles TO alter_ego_app` after `REVOKE UPDATE ON profiles` |

**Optional tiny expansion (not required):** `core/settings.py` `migration_database_url` field for cleaner compose — defer unless inline override proves brittle.

### Dead ends

- **Full profile INSERT-only without code changes:** blocked by supersede/promote UPDATE paths above.
- **RLS for audit:** SPEC §9.2 mentions RLS "where applicable"; table/column grants suffice for v1; RLS adds complexity with no current app support.
- **pytest enforcement:** all tests use SQLite in-memory — DB role behavior is **compose/manual verification** unless a live Postgres test is added (out of packet scope).

## Implementer brief — Path A

### Write scope (only these paths)

- `alembic/versions/<new>_add_app_db_roles.py`
- `docker-compose.yml`
- `docs/SPEC.md` (§9.2 mechanism — mark shipped; resolve §685 debate note)
- `docs/SPEC_V3.md` (§6.3 lifecycle-column exception; §259 wording)
- `docs/deployment.md` (role matrix, DSN split, verification recipe)
- `memory-bank/progress.md` (S5.3 row)

**Do not edit** `worker/`, `core/models.py`, `batch/profile_builder/builder.py`, or tests unless verifier finds compose wiring impossible without `settings` change.

### Acceptance criteria

1. **Migration** creates role `alter_ego_app` (password from compose env, e.g. `ALTER_EGO_APP_PASSWORD`) and grants:
   - `SELECT, INSERT` on `audit_logs`, `decisions`, `explanations`, `scoring_configs`; `REVOKE UPDATE, DELETE`
   - `SELECT, INSERT` on `profiles`; `UPDATE (promoted_at, superseded_at)` only; `REVOKE DELETE`
   - `SELECT, INSERT, UPDATE` on `alert_workflow_state`, `containment_queue`, `events`, `resolved_events`, `eval_ground_truth` as needed for documented compose workflows
   - `USAGE, SELECT` on required sequences
2. **Compose** runs migrations as owner `user`; `web`/`worker`/`batch` runtime `DATABASE_URL` uses `alter_ego_app`.
3. **Docs** state explicitly: profile **payload** immutability via column grants; lifecycle columns updated only at promotion; not full table INSERT-only until promotion redesign.
4. **Verification recipe** in `docs/deployment.md`: after `docker compose up`, connect as `alter_ego_app` and confirm `INSERT INTO audit_logs …` succeeds, `UPDATE audit_logs …` fails, `UPDATE profiles SET features=…` fails, `UPDATE profiles SET superseded_at=now() …` succeeds (on an existing row), profile build + promotion still works.
5. **`pytest` + `ruff`** remain green (SQLite tests unaffected).
6. **No false claims** in SPEC/SPEC_V3/deployment that profiles are table-level INSERT-only.

### Open questions for implementer

- Whether `eval_ground_truth` DELETE in `batch/eval/runner.py` warrants a separate `alter_ego_batch` role vs documenting owner DSN for eval sweeps.
- Whether to include `decisions`/`explanations`/`scoring_configs` in the "audit/commit" grant set (recommended — all insert-only in code and strengthens §9.2 story).
